# Yatk v2 優先実行仕様

## この文書について

この文書は、Yatk v1 に優先実行機能を追加するための仕様書です。
記載のない動作は `v1-spec.md` を引き継ぎます。

v2 では、通常の FIFO 実行に加えて、利用者がジョブごとに次の実行方針を指定できるようにします。

- 通常の待機キューへ投入する
- 通常の待機ジョブより先に実行する
- 最大並列度に空きがなくても直ちに実行する

実行中ジョブの中断、プリエンプション、永続化、複数の実行レーンは v2 の対象外です。

## 目的

通常の最大並列度制御を維持しながら、利用者が必要に応じて次の要求を表現できるようにします。

1. 実行枠が空いたとき、通常の待機ジョブより先に開始してほしい。
2. 現在の実行数にかかわらず、投入後すぐに開始してほしい。

この機能は、ジョブの重要度を無制限な数値で表現する汎用優先度システムではありません。v2 では、挙動が明確な少数の実行方針だけを公開します。

## 公開 API

### `YatkJobPriority`

ジョブ投入時の優先度を表す列挙型を追加します。

```csharp
public enum YatkJobPriority
{
    Normal,
    High,
    Immediate,
}
```

各値の意味は次のとおりです。

#### `Normal`

- v1 と同じ通常の FIFO 待機キューへ投入する。
- `MaxConcurrency` に空きがある場合は速やかに開始する。
- 既定値とする。

#### `High`

- 実行枠が空くまで待機する。
- 待機中の `Normal` ジョブより先に選択する。
- すでに実行中のジョブは中断しない。
- `MaxConcurrency` を超えて開始しない。

#### `Immediate`

- 待機キューへ入れず、投入後に直ちに開始する。
- 現在の実行数が `MaxConcurrency` 以上でも開始する。
- すでに実行中のジョブは中断しない。
- 専用スレッドは作成せず、v1 と同じ実行基盤を使用する。

未知の列挙値は `ArgumentOutOfRangeException` として拒否してください。

### 投入 API

既存 API との互換性を保つため、優先度を省略した場合は `Normal` とします。

候補 API：

```csharp
public YatkJobId Enqueue(
    YatkJobBase job,
    YatkJobPriority priority = YatkJobPriority.Normal);

public YatkJobId Do(
    Func<YatkJobContext, CancellationToken, Task> action,
    string? name = null,
    YatkJobPriority priority = YatkJobPriority.Normal);
```

オーバーロード解決が曖昧になる場合は、既存 API を残したうえで優先度を必須引数とする別オーバーロードを追加して構いません。

`YatkJobBase` のインスタンス自体には優先度を保持させません。優先度は一回限りの投入要求に対する指定として扱います。

## 待機順序

待機中ジョブの選択順は、次の規則に従います。

1. `High` の待機ジョブ
2. `Normal` の待機ジョブ

同じ優先度内では投入順の FIFO とします。

`High` ジョブを複数回投入した場合、後から投入したジョブが先に投入済みの `High` ジョブを追い越してはいけません。これは、単純に一つのリストの先頭へ挿入して LIFO にするのではなく、優先待機領域内の末尾へ追加することを意味します。

例：

```text
投入順: Normal A, Normal B, High C, High D
開始順: High C, High D, Normal A, Normal B
```

ただし、投入時点ですでに開始済みのジョブは追い越しの対象になりません。

`High` が継続的に投入された場合、`Normal` が長時間開始されない可能性があります。v2 ではエージングや公平性制御を追加しません。

## `Immediate` の実行モデル

`Immediate` は最大並列度の一時変更ではありません。

- `MaxConcurrency` の設定値は変更しない。
- `MaxConcurrency` プロパティも変更しない。
- `Immediate` ジョブも実行中ジョブ数へ含める。
- `Immediate` ジョブの開始によって通常の実行枠が増えたものとは扱わない。

例えば `MaxConcurrency == 2` で通常ジョブが 2 件実行中のときに `Immediate` を投入すると、一時的な実行数は 3 件になります。

この状態でいずれかのジョブが完了しても、実行中ジョブ数が `MaxConcurrency` 以上である間は、待機中の `High` および `Normal` ジョブを新たに開始しません。

```text
MaxConcurrency = 2
通常実行中 = 2
Immediate を投入 → 実行中 = 3
1 件完了          → 実行中 = 2、待機ジョブは開始しない
さらに 1 件完了   → 実行中 = 1、待機ジョブを 1 件開始する
```

複数の `Immediate` ジョブが同時または連続して投入された場合、それぞれを直ちに開始します。そのため、実行数の超過量に上限は設けません。リソース枯渇を招く可能性があることを XML ドキュメントコメントと README に明記してください。

「直ちに開始」とは、同期的にジョブ本体を実行することではありません。投入処理の同期範囲内で `Running` へ遷移させ、v1 と同じ方法で非同期実行をスケジュールすることを意味します。OS または ThreadPool による実際の実行開始時刻は保証しません。

## 状態とスナップショット

すべての優先度で、状態遷移は v1 と同じものを使用します。

```text
Created -> Queued -> Running -> Succeeded / Failed
                         |
                         -> CancelRequested -> Canceled / Succeeded / Failed
```

`High` と `Normal` は投入時に `Queued` へ遷移します。

`Immediate` も、イベントと時刻の一貫性を保つため、投入時に一度 `Queued` へ遷移してから `Running` へ遷移します。ただし、通常動作では待機キューに保持されません。

`Queued` と `Running` の `JobChanged` は、この順序で通知キューへ記録してください。

スナップショットへ `Priority` を追加し、投入時に指定された値を観測できるようにします。

```csharp
public sealed record YatkJobSnapshot(
    YatkJobId JobId,
    string? Name,
    YatkJobPriority Priority,
    YatkJobState State,
    // v1 から引き継ぐその他の値
);
```

これは公開スナップショットの形を変更します。ソース互換性への影響を避ける必要がある場合は、位置引数を変更せず読み取り専用プロパティとして追加する方法も検討してください。

## キャンセル

`Normal` と `High` の待機中キャンセルは v1 と同じです。

- 待機領域から物理的に削除する。
- `Canceled` へ遷移する。
- ジョブ本体を実行しない。

`Immediate` は投入処理中に `Running` へ遷移するため、投入 API が正常に戻った後のキャンセルは原則として実行中ジョブの協調キャンセルになります。

キャンセルと実行開始が競合した場合の状態遷移規則は v1 を引き継ぎます。

## 最大並列度の動的変更

`SetMaxConcurrency` の基本動作は v1 と同じです。

- 増加時は、空いた通常実行枠へ `High`、`Normal` の順で待機ジョブを開始する。
- 減少時は、実行中ジョブを停止しない。
- 実行中ジョブ数が新しい上限未満になるまで待機ジョブを開始しない。
- `Immediate` は変更後の上限にかかわらず開始できる。

実行中の `Immediate` ジョブも、上限未満かどうかを判定する実行中ジョブ数へ含めます。

## Graceful Shutdown

停止開始後は、すべての優先度で新規投入を拒否します。

### `Drain`

- 実行中の `Immediate` ジョブを含む、登録済みの全ジョブを待つ。
- 待機中ジョブは `High`、`Normal` の順に実行する。
- 通常の最大並列度を守る。

### `Cancel`

- 待機中の `High` と `Normal` をキャンセルする。
- 実行中の `Immediate` を含む全実行中ジョブへキャンセルを要求する。
- すべての実行中ジョブが終了するまで待つ。

停止開始と `Immediate` 投入が競合した場合は、v1 と同様にスケジューラの同期範囲で先に成立した操作を採用します。

## 内部実装要件

具体的なデータ構造は限定しませんが、少なくとも次の性質を満たしてください。

- `High` と `Normal` の選択順が明確である。
- 各優先度内で FIFO を維持する。
- 待機中キャンセルで対象を O(1) で物理削除できる。
- 優先度の選択や `Immediate` の開始判定を公開 API の各所へ重複させない。
- 状態遷移、実行中数、停止状態を v1 と同じ同期方針で保護する。
- ロック中にジョブ本体やイベントハンドラを実行しない。

実装候補として、優先度ごとに `LinkedList<JobEntry>` を保持する方法、または一つのリスト内に優先領域と通常領域を持つ方法があります。

数値優先度や汎用の比較器は追加しないでください。

## テスト

時間依存の待機ではなく、`TaskCompletionSource` などで実行枠の占有と解放を制御してください。

### 互換性

- 優先度を省略した投入が v1 と同じ `Normal` 動作になる。
- 既存の FIFO、キャンセル、停止、保持上限のテストが成功する。

### `High`

- 実行枠が埋まっている場合は待機する。
- 待機中の `Normal` より先に開始する。
- 複数の `High` が FIFO 順に開始する。
- すでに実行中の `Normal` を中断しない。
- 待機中にキャンセルすると実行されない。
- `MaxConcurrency` を超えない。

### `Immediate`

- 実行枠に空きがなくても開始する。
- `MaxConcurrency` の値を変更しない。
- 複数件を投入すると、その件数分だけ上限を超えて開始できる。
- `Immediate` により上限以上となっている間、待機ジョブを追加開始しない。
- 完了後、実行数が上限未満になると待機ジョブを再開する。
- 実行中キャンセルが協調キャンセルとして動作する。
- `Drain` が完了を待つ。
- `Cancel` がキャンセルを要求する。

### 状態とイベント

- スナップショットから指定した優先度を取得できる。
- `Immediate` でも `Queued`、`Running` の順にイベントが発生する。
- 保持上限による削除がすべての優先度で同じように動作する。
- 未定義の優先度を拒否する。

### 競合条件

- `High` 投入と実行枠解放の競合。
- `Immediate` 投入と停止開始の競合。
- `Immediate` 完了と最大並列度変更の競合。
- 優先度の異なるジョブの同時投入。
- 待機中 `High` のキャンセルと実行開始の競合。

## README 更新要件

実装時には README に次を追記してください。

- `Normal`、`High`、`Immediate` の違い。
- `High` は実行中ジョブを中断しないこと。
- `Immediate` は最大並列度を超えること。
- `Immediate` の連続投入には超過上限がなく、利用者がリソース消費を管理する必要があること。
- FIFO の保証は同じ優先度内の実行枠への割り当て順であり、ThreadPool 上でユーザーコードが実際に動き始める順序までは保証しないこと。

## 完了条件

以下をすべて満たした時点で v2 の優先実行機能を完了とします。

- 優先度を省略した既存コードが v1 と同じ動作をする。
- `High` が通常の待機ジョブより先に選択される。
- `High` 内と `Normal` 内で FIFO が維持される。
- `Immediate` が最大並列度を超えて開始できる。
- `Immediate` 実行中も、通常の実行枠制御が破綻しない。
- キャンセル、完了待機、イベント、保持上限、停止処理がすべての優先度で機能する。
- 公開 API に XML ドキュメントコメントがある。
- README と実装進捗が更新されている。
- 追加テストと既存テストがすべて成功する。

## 将来検討

以下は v2 の対象外とします。

- 任意の数値優先度。
- 優先度の動的変更。
- 待機時間に応じた優先度の引き上げ。
- `Normal` の starvation 防止。
- `Immediate` の超過数制限。
- 実行中ジョブのプリエンプション。
- 実行レーンごとの優先度と並列度。
- 専用スレッドでの即時実行。
