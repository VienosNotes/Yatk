# Yatk 初期実装指示

この指示は、Yatk の基礎機能を実装するうえでの最終的なゴールを示しています。
このドキュメントと併せて別途提示するYatkのコンセプトに従い、最小構成のインメモリジョブスケジューラを実装してもらいます。
指示は個別に小さい粒度で段階的に行うため、この内容を一度にすべて実装する必要はありません。


初期実装では、通常のThreadPool上で実行する単一のジョブキューのみを対象とします。永続化、分散実行、複数の実行レーン、専用スレッド実行、中断・再開などは実装しません。

将来の拡張を妨げない責務分離は行いますが、未使用の抽象化や拡張ポイントを先回りして大量に作らないでください。

# Codexへの作業ルール

このドキュメントは、**仕様書**であると同時に**実装進捗管理**にも利用します。

## 基本ルール

- 仕様本文は原則として変更しないでください。
- 実装状況は、このドキュメント内へ追記して管理してください。
- 仕様変更が必要だと判断した場合は、仕様本文を書き換えず、各項目の `Notes` に提案として記載してください。
- 実装中に気付いた改善点や懸念事項も `Notes` に記載してください。

---

## 各項目への進捗記録

各実装項目の直下に、以下の形式で進捗を記録してください。

```text
Status:
Notes:
```

### Status

以下のいずれかのみを使用してください。

- ⬜ Not started
- 🚧 In progress
- 🟨 Partially implemented
- ✅ Implemented
- ⚠️ Blocked

### Notes

必要に応じて自由に追記してください。

以下の内容を推奨します。

- 実装方針
- 実装したクラスやファイル
- 追加したテスト
- 仕様との差異
- 今後の課題
- 判断に迷った点

---

## Status の判定基準

### ⬜ Not started

未着手。

---

### 🚧 In progress

実装途中。

まだ動作保証やテストが完了していない。

---

### 🟨 Partially implemented

主要部分は実装済みだが、未対応項目や既知の制限が残っている。

必ず `Notes` に未完了内容を記載してください。

---

### ✅ Implemented

以下をすべて満たした場合のみ設定してください。

- 実装済み
- ビルド成功
- 対応するテストを追加済み
- テスト成功
- 既知の未対応事項が残っていない

---

### ⚠️ Blocked

実装を続行できない問題がある場合。

必ず `Notes` に理由を記載してください。

## 初期実装の対象

```text
Status: 🟩 Implemented
Notes:
Implementation:
- ラムダジョブ、YatkJobBase 派生ジョブ、FIFO キュー、固定最大並列度を実装した。
- `YatkJobId`、`YatkJobState`、`YatkJobSnapshot` を追加し、`Queued`、`Running`、`Succeeded`、`Failed` の状態遷移と時刻・例外の記録を実装した。
- `Enqueue` と `Do` が `YatkJobId` を返すようにし、`GetJob` と `GetJobs` で読み取り専用スナップショットを取得できるようにした。
- `Cancel` を追加し、待機中ジョブのスキップと実行中ジョブへの協調キャンセルを実装した。
- 実行中ジョブのキャンセルは `Running` から `CancelRequested` を経由し、該当ジョブのトークンによるキャンセル例外だけを `Canceled` として記録する。
- `WaitForCompletionAsync` を追加し、ジョブの終了状態までポーリングなしで待機できるようにした。
- `YatkJobContext` を追加し、ジョブから進捗と状態メッセージを報告してスナップショットへ反映できるようにした。
- `JobChanged` イベントを追加し、状態変更時にスナップショットを FIFO の通知キューへ記録してから、ロック外で一件ずつ通知するようにした。イベントハンドラの例外はスケジューラの動作へ影響しない。
- `StopAsync` を追加し、`Drain` と `Cancel` による停止を実装した。`DisposeAsync` は `Cancel` 相当で停止する。
- `YatkSchedulerOptions`、`MaxConcurrency`、`SetMaxConcurrency` を追加し、実行中の最大並列度変更を実装した。増加時は待機中ジョブを追加で開始し、減少時は実行中ジョブを停止せず以後の開始を抑制する。
- 実行管理は FIFO 待機キューと実行枠の管理に分離し、動的な並列度変更と停止処理を同じ同期範囲で扱うようにした。
- `MaxRetainedCompletedJobs` を追加し、完了済みジョブを設定件数まで保持して最古のものから削除するようにした。`WaitForCompletionAsync` は、未登録または削除済みの ID に対して `false` を返す。
- 待機中ジョブのキャンセル時は、待機キューから対象ノードを物理削除するようにした。これにより、実行枠が埋まっている間もキャンセル済みジョブの参照を待機キューに保持しない。
- キャンセル要求と完了済みジョブ削除の競合で CTS が先に破棄済みの場合は、キャンセル通知を不要として扱い、例外を外部へ送出しないようにした。
- ジョブ本体の完了後に `YatkJobContext` が外部から利用されても、進捗および状態メッセージの更新を無視するようにした。
- `YatkJobContext` の更新と無効化を同じ同期範囲で扱い、完了処理と同時に開始された更新が完了後のスナップショットを書き換えないようにした。
- キャンセル通知を `JobChanged` のハンドラ呼び出しより先に行い、ハンドラの処理時間によってジョブのキャンセルが遅延しないようにした。
- `StopAsync` は未定義の `YatkShutdownMode` を `ArgumentOutOfRangeException` として拒否するようにした。

Tests:
- ラムダジョブ、YatkJobBase 派生ジョブ、FIFO、最大並列度、例外後の継続、状態遷移、例外記録、スナップショット一覧、待機中・実行中ジョブのキャンセル、完了待機、進捗・状態メッセージの報告、イベント、停止処理、動的並列度変更、同時投入、完了済みジョブの保持上限を検証するテストを追加した。
- ジョブ完了とコンテキスト更新の競合後に、完了済みスナップショットが変化しないことを検証するテストを追加した。
- `dotnet test Yatk.sln --no-restore` が成功した（37 件）。

Deviations:
- 正規の非同期デリゲートおよび派生ジョブの戻り値は、`ValueTask` ではなく `Task` とした。
- `IYatkJob` は、公開投入対象を `YatkJobBase` に限定するため追加しない。

Follow-ups:
- `ValueTask` 形式の API を追加または `Task` 形式を初期版の正式 API として確定する。
```

以下の機能を実装してください。

- リッチジョブの投入
- ラムダによる単発ジョブの投入
- FIFO順での実行
- 最大並列度の制御
- 最大並列度の動的変更
- ジョブ状態の取得
- ジョブ一覧のスナップショット取得
- 待機中ジョブのキャンセル
- 実行中ジョブの協調キャンセル
- ジョブ完了の待機
- 状態変化イベント
- Graceful Shutdown
- ジョブ例外の捕捉と記録

## 現状判明している懸念

1. 低: `JobChanged` の厳密な到着順を公開 API だけで決定的に検証するテストは未追加です。通知キューへの記録は同一ロック内で行うため実装上は順序を保証しますが、複数スレッドからの実際の呼び出し順を外部テストで固定するには、通知キューの内部フックが必要になります。初期版ではテスト専用の公開 API を増やさず、既存の状態遷移テストで間接的に確認します。

## ジョブの基本モデル

ジョブは再利用可能な定義ではなく、一回限りの実行要求オブジェクトとして扱います。

一度スケジューラへ投入されたジョブインスタンスは、同じスケジューラにも別のスケジューラにも再投入できないものとします。

二度目の投入を試みた場合は、明示的な例外を送出してください。

ジョブは自身の実行状態を保持して構いません。ただし、主要な状態遷移はスケジューラまたは内部ランナーだけが実行できるようにし、派生ジョブから任意の状態へ変更できないようにしてください。

## 必要な公開型

### `YatkJobId`

ジョブを識別する専用の値型です。

`Guid`を内部値として使用して構いませんが、公開APIで生の`Guid`をジョブIDとして扱わないでください。

候補形：

```csharp
public readonly record struct YatkJobId(Guid Value);
```

文字列表現が必要な場合は、通常の`Guid`表現で構いません。

### `YatkJobState`

最低限、以下の状態を持たせてください。

```csharp
public enum YatkJobState
{
    Created,
    Queued,
    Running,
    CancelRequested,
    Succeeded,
    Failed,
    Canceled
}
```

状態の意味は以下のとおりです。

- `Created`: ジョブオブジェクト生成後、未投入
- `Queued`: 投入済みで実行待ち
- `Running`: 実行中
- `CancelRequested`: 実行中でキャンセル要求済み
- `Succeeded`: 正常終了
- `Failed`: 例外による失敗
- `Canceled`: キャンセル完了

終了状態は`Succeeded`、`Failed`、`Canceled`です。

### `IYatkJob`

リッチジョブの最小契約です。

```csharp
public interface IYatkJob
{
    ValueTask ExecuteAsync(
        YatkJobContext context,
        CancellationToken cancellationToken);
}
```

ただし、一回限りの投入制約や状態保持をインターフェースだけでは安全に実現しにくい場合は、初期版では公開投入対象を`YatkJobBase`に限定しても構いません。

その場合でも、内部の実行契約として`IYatkJob`を使用するかどうかは、実装を不必要に複雑にしない範囲で判断してください。

### `YatkJobBase`

リッチジョブを実装するための抽象基底クラスです。

最低限、以下を提供してください。

- JobId
- 現在状態
- 表示名
- 進捗
- 状態メッセージ
- 投入済みかどうかの管理
- 実行メソッド
- 内部限定の状態遷移操作

派生クラスが実装するのは実行処理です。

例：

```csharp
public abstract class YatkJobBase
{
    public YatkJobId JobId { get; }
    public YatkJobState State { get; }
    public string? Name { get; }
    public double? Progress { get; }
    public string? StatusMessage { get; }

    protected abstract ValueTask ExecuteAsync(
        YatkJobContext context,
        CancellationToken cancellationToken);
}
```

具体的な可視性やインターフェース実装方法は調整して構いません。

ただし、派生クラスから次のような操作ができないようにしてください。

```csharp
State = YatkJobState.Succeeded;
```

成功、失敗、キャンセルなどの状態は、実行結果を観測したスケジューラ側が決定します。

### `YatkJobContext`

ジョブ実行中に利用するコンテキストです。

初期版では以下だけを提供してください。

- JobId
- 進捗報告
- 状態メッセージ更新

候補API：

```csharp
public sealed class YatkJobContext
{
    public YatkJobId JobId { get; }

    public void ReportProgress(double progress);

    public void SetStatusMessage(string? message);
}
```

進捗値は`0.0`から`1.0`までとし、範囲外の値を渡した場合の挙動を明確にしてください。初期版では`ArgumentOutOfRangeException`で構いません。

`YatkJobContext`へDIサービス、ロガー、スケジューラ本体などを持たせないでください。

### `YatkJobSnapshot`

問い合わせ結果として返す、読み取り専用のスナップショットです。

最低限、以下を含めてください。

```text
JobId
Name
State
Progress
StatusMessage
QueuedAt
StartedAt
CompletedAt
Exception
```

`Exception`をそのまま返すか、例外情報用の型へ変換するかは初期版ではどちらでも構いません。

ただし、問い合わせによってジョブ実体そのものを外部へ返さないでください。

スナップショット取得中に状態が変化しても、返却されたオブジェクト内では一貫した値になるようにしてください。

### `YatkSchedulerOptions`

最低限、初期最大並列度を設定できるようにしてください。

```csharp
public sealed class YatkSchedulerOptions
{
    public int MaxConcurrency { get; init; } = 1;
    public int MaxRetainedCompletedJobs { get; init; } = 1000;
}
```

最大並列度は1以上とします。完了済みジョブの保持件数は0以上とし、0の場合は完了と同時にスケジューラから削除します。

### `YatkScheduler`

利用者が操作する中心APIです。

最低限、以下に相当する操作を提供してください。

```csharp
public sealed class YatkScheduler : IAsyncDisposable
{
    public YatkJobId Enqueue(YatkJobBase job);

    public YatkJobId Do(
        Func<YatkJobContext, CancellationToken, ValueTask> action,
        string? name = null);

    public bool Cancel(YatkJobId jobId);

    public YatkJobSnapshot? GetJob(YatkJobId jobId);

    public IReadOnlyList<YatkJobSnapshot> GetJobs();

    public Task<bool> WaitForCompletionAsync(
        YatkJobId jobId,
        CancellationToken cancellationToken = default);

    public void SetMaxConcurrency(int maxConcurrency);

    public Task StopAsync(
        YatkShutdownMode mode,
        CancellationToken cancellationToken = default);

    public ValueTask DisposeAsync();
}
```

正確なメソッド名や戻り値は、整合性が高くなる範囲で調整して構いません。

ただし、利用者が以下を自然に実行できるAPIにしてください。

```csharp
var scheduler = new YatkScheduler(
    new YatkSchedulerOptions
    {
        MaxConcurrency = 2
    });

var id = scheduler.Do(
    async (context, cancellationToken) =>
    {
        context.SetStatusMessage("処理中");
        await SomeOperationAsync(cancellationToken);
        context.ReportProgress(1.0);
    },
    name: "サンプルジョブ");

var snapshot = scheduler.GetJob(id);

scheduler.Cancel(id);

if (!await scheduler.WaitForCompletionAsync(id))
{
    // ジョブは未登録または保持期限切れです。
}
```

## ラムダジョブ

ラムダによるジョブは、内部の非公開ジョブ型へラップし、リッチジョブと完全に同じ実行経路へ流してください。

初期版で必須の正規形は以下です。

```csharp
Func<YatkJobContext, CancellationToken, ValueTask>
```

利用性のため、以下のような補助オーバーロードを少数追加しても構いません。

```csharp
Func<CancellationToken, Task>
Func<CancellationToken, ValueTask>
Func<Task>
Func<ValueTask>
Action
```

ただし、オーバーロード解決が曖昧になるほど増やさないでください。

内部では正規形へ変換してください。

## スケジューリング

初期版は単一のFIFOキューとします。

ジョブは投入順に実行してください。

ただし、キャンセル済みジョブをスキップした結果として、厳密な連番順にならないことは許容します。

実行中ジョブ数が最大並列度未満で、待機中ジョブが存在する場合に、新しいジョブを開始してください。

### 最大並列度の動的変更

最大並列度は実行中に変更可能としてください。

増加時：

- 空き枠が増えた場合は、待機中ジョブを速やかに開始する

減少時：

- 既に実行中のジョブは停止しない
- 実行中ジョブ数が新しい上限を下回るまで、新しいジョブを開始しない

例えば、実行中ジョブが2件のとき最大並列度を1へ変更しても、既存の2件はそのまま完走させてください。

最大並列度0は初期版では許可しません。

## キャンセル

### 待機中ジョブ

`Queued`状態のジョブにキャンセル要求が来た場合は、実行せず`Canceled`へ遷移させてください。

待機中ジョブへのキャンセルは、状態を`Canceled`へ遷移させたうえで、待機キューから物理的に削除してください。
これにより、実行枠が空くまでキャンセル済みジョブやその参照が待機キューに残らないようにしてください。

### 実行中ジョブ

`Running`状態のジョブにキャンセル要求が来た場合は、

1. `CancelRequested`へ遷移
2. そのジョブ専用の`CancellationTokenSource`をキャンセル
3. ジョブ終了時に結果を判定

としてください。

ジョブがキャンセル要求を無視して正常終了した場合の最終状態は、初期版では`Succeeded`として構いません。

`OperationCanceledException`または`TaskCanceledException`が、当該ジョブのキャンセルトークンに基づいて発生した場合は`Canceled`としてください。

無関係な`OperationCanceledException`まで自動的に`Canceled`へ分類しないよう注意してください。

終了済みジョブへのキャンセルは状態を変更せず、`false`を返すなど、結果が判別できるようにしてください。

## 例外処理

ジョブから送出された未処理例外は、スケジューラ全体へ伝播させず、そのジョブを`Failed`へ遷移させて記録してください。

あるジョブの失敗によって、後続ジョブの実行が停止しないようにしてください。

ジョブ例外が未監視Task例外にならないようにしてください。

## 完了待機

JobIdを指定して、そのジョブが終了状態になるまで待機できるようにしてください。

正常終了、失敗、キャンセルのいずれでも待機自体は正常に完了する設計で構いません。

ジョブの成否は完了後のスナップショットで確認する方式としてください。

待機開始時に存在しない、または完了済みジョブの保持上限により削除済みのJobIdを指定した場合は、`false`を返してください。
待機開始時にジョブが存在した場合は、その後に保持上限により削除されても、待機は通常どおり完了して`true`を返してください。

待機側の`CancellationToken`は、ジョブそのものをキャンセルせず、完了待機だけを中断するものとします。

## 状態変化イベント

最低限、ジョブ状態が変化したことを通知するイベントを一つ提供してください。

候補：

```csharp
public event EventHandler<YatkJobChangedEventArgs>? JobChanged;
```

イベント引数には最低限、JobIdと変更後のスナップショットを含めてください。イベント引数のスナップショットを、その通知が表す状態の正とします。

イベントは状態を保存した後に発火してください。状態遷移ごとの通知は遷移した順序で FIFO に配送し、一度に一つのイベントハンドラだけを実行してください。

完了済みジョブの保持上限が 0 の場合、完了状態のイベントを受け取った時点でも `GetJob(eventArgs.JobId)` は `null` になり得ます。この場合もイベント引数のスナップショットは有効であり、イベントハンドラはそれを利用してください。

イベントハンドラが例外を送出しても、ジョブ実行やスケジューラ制御ループを壊さないようにしてください。

初期版では通知の配送保証や再送は不要です。

正しい現在状態は常に問い合わせAPIから取得するものとします。ただし、保持上限によって削除済みのジョブについては問い合わせAPIから取得できません。

イベントハンドラは専用スレッドを使用せず、通知の配送を開始した呼び出しスレッド上で同期的に実行します。すでに配送中の場合、後続の通知はその配送スレッドが続けて実行します。イベントハンドラはロック外で実行し、購読者例外は隔離してください。

## Graceful Shutdown

停止処理には最低限、次の二つの方針を用意してください。

```csharp
public enum YatkShutdownMode
{
    Drain,
    Cancel
}
```

### `Drain`

- 新規ジョブ投入を拒否する
- 待機中ジョブを含め、登録済みジョブをすべて実行する
- 実行中および待機中ジョブがすべて終了するまで待つ

### `Cancel`

- 新規ジョブ投入を拒否する
- 待機中ジョブをキャンセルする
- 実行中ジョブへキャンセル要求を送る
- すべての実行中ジョブが終了するまで待つ

停止処理中および停止後の`Enqueue`と`Do`は、明示的な例外で拒否してください。

`StopAsync`は複数回呼び出しても壊れないようにしてください。

`DisposeAsync`の既定動作は`Cancel`相当で構いません。

ユーザー指定のCancellationTokenによって`StopAsync`の待機が打ち切られても、内部の停止処理そのものを不整合な状態へ戻さないでください。

## 内部コンポーネント

最初から各責務をすべて別クラスへ分割する必要はありませんが、少なくとも概念上は以下を分離してください。

### ジョブレジストリ

JobIdからジョブおよび内部実行情報を取得します。

以下を担当します。

- ジョブ登録
- JobId検索
- スナップショット生成
- ジョブ一覧取得

完了済みジョブは `YatkSchedulerOptions.MaxRetainedCompletedJobs` の件数まで完了順に保持してください。
上限を超えた場合は、最も古く完了したジョブから登録一覧およびスケジューラが保持するジョブ参照を削除してください。
削除済みジョブは `GetJob` から取得できず、`Cancel` は `false` を返し、`WaitForCompletionAsync` は `false` を返します。

### 待機キュー

FIFO順でジョブを保持します。

実装には`Channel<T>`などを使用して構いません。

ただし、最大並列度の動的変更、待機中キャンセル、停止処理が不自然になる場合は、特定のデータ構造へ固執しないでください。
待機中ジョブを O(1) で物理削除できる必要があるため、必要に応じてノード参照を保持するリスト構造などを使用してください。

キューの具体的な型を公開APIへ漏らさないでください。

### 実行ポンプ

以下を担当する内部ループまたは内部処理を用意してください。

- 実行中数の管理
- 最大並列度との比較
- 待機ジョブの取得
- ジョブ開始
- ジョブ完了時の次ジョブ起動

固定数の常駐ワーカー方式でも、空き枠に応じてTaskを開始するポンプ方式でも構いません。

ただし、最大並列度の減少を自然に扱える方式を選んでください。

### ジョブ実行処理

一件のジョブについて、以下を一か所で行ってください。

1. `Running`への遷移
2. 実行時刻記録
3. `YatkJobContext`生成
4. ジョブ処理の呼び出し
5. 正常終了、例外、キャンセルの分類
6. 終了状態への遷移
7. 完了時刻記録
8. 完了待機の解放
9. 次のジョブを開始できることの通知

## スレッドセーフティ

以下の操作は、複数スレッドから同時に呼び出されても安全にしてください。

- ジョブ投入
- キャンセル
- 状態取得
- 一覧取得
- 最大並列度変更
- 停止開始
- 進捗報告
- 状態メッセージ更新

ジョブ状態、時刻、進捗、メッセージが別々の時点の値として不整合に見えないよう、スナップショット生成時の同期方法を設計してください。

公開コレクションとして変更可能な内部コレクションを返さないでください。

ロック中にユーザーコードを実行しないでください。

ユーザーコードには以下を含みます。

- ジョブ本体
- イベントハンドラ
- 外部デリゲート

## テスト

少なくとも以下のテストを実装してください。

### 基本実行

- ラムダジョブが実行される
- `YatkJobBase`派生ジョブが実行される
- 投入順に実行される
- 正常終了時に`Succeeded`になる
- 例外発生時に`Failed`になる
- 一つのジョブ失敗後も後続ジョブが実行される

### 並列度

- 実行中ジョブ数が最大並列度を超えない
- 最大並列度を増やすと待機ジョブが開始される
- 最大並列度を減らしても実行中ジョブは中断されない
- 減少後、実行数が上限以下になるまで新規ジョブが始まらない

時間依存の不安定なテストを避け、`TaskCompletionSource`などで開始・解放タイミングを制御してください。

### キャンセル

- 待機中ジョブをキャンセルすると実行されない
- 実行中ジョブへCancellationTokenが伝播する
- 協調キャンセル後に`Canceled`になる
- キャンセルを無視して正常終了したジョブの状態が仕様どおりになる
- 終了済みジョブへのキャンセルが状態を変えない
- 重複キャンセルで壊れない

### 状態と問い合わせ

- 状態遷移が正しい
- 時刻が適切に記録される
- 進捗報告がスナップショットへ反映される
- 状態メッセージが反映される
- 範囲外の進捗値が拒否される
- ジョブ一覧が取得できる
- 返されたスナップショットから内部状態を変更できない

### 一回限りの投入

- 同じジョブインスタンスを二度投入できない
- 異なるスケジューラへ同じジョブを投入しても拒否される
- 投入失敗時にジョブが不必要に使用済みにならない

最後の点については、スケジューラ停止済みなどの理由で投入を受け付けられなかった場合、ジョブを再度別の稼働中スケジューラへ投入できる設計が望ましいです。投入済みフラグを立てるタイミングに注意してください。

### 完了待機

- 正常終了を待機できる
- 失敗終了を待機できる
- キャンセル終了を待機できる
- 待機側だけをCancellationTokenで中断できる
- 待機側の中断がジョブ本体をキャンセルしない

### イベント

- 状態変化時にイベントが発生する
- イベント引数のスナップショットが変更後の状態を表す
- 保持上限 0 の完了イベントでは問い合わせ結果が `null` になり得る
- イベントハンドラの例外でスケジューラが停止しない

### Shutdown

- `Drain`で待機中を含む全ジョブが完了する
- `Cancel`で待機中ジョブがキャンセルされる
- `Cancel`で実行中ジョブへキャンセル要求が届く
- 停止開始後に新規投入できない
- `StopAsync`を複数回呼び出しても壊れない
- `DisposeAsync`で停止できる

### 競合条件

可能な範囲で以下の競合をテストしてください。

- キャンセルと実行開始の同時発生
- キャンセルと正常終了の同時発生
- 並列度変更とジョブ完了の同時発生
- 停止開始とジョブ投入の同時発生
- 複数スレッドからの同時投入

## 実装方針

最初に公開APIと状態遷移を定義し、それから内部実装へ進んでください。

状態遷移を暗黙の条件分岐として各所へ散らさず、一か所または少数の内部メソッドへ集約してください。

`Task.Run`、ロック、`SemaphoreSlim`、`Channel<T>`などを無目的に組み合わせないでください。それぞれが何を保護または制御しているかを明確にしてください。

ポーリングや短い待機時間に依存する実装およびテストは避け、状態変化を通知する仕組みを使用してください。

性能最適化よりも、状態遷移、キャンセル、並列度、停止処理の正しさを優先してください。

過剰な汎用化は避けてください。将来の実行レーン対応を想定しても、初期版で`IExecutionLane`などの抽象を導入する必要はありません。

ただし、ジョブを実行する処理と、ジョブの投入・問い合わせを受け付ける公開ファサードは、後から分離できる構造にしてください。
